### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the forge for PR create, edit, view, watch, and merge operations. Never require Graphite (`gt`). One owner per PR, in its own worktree, owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle, `{{p3}}/principles/principle-prove-it-works.md`), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (deslop per [the runtime's Missing companions](../references/runtime.md#missing-companions)), `/p3:no-comments` (the **no-comments** skill, `{{p3}}/skills/no-comments/SKILL.md`), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. In T3 each owner is a launched thread per [the runtime's Isolation](../references/runtime.md#isolation). Launch it with `t3_thread_launch`, a `worktree` `workspaceStrategy` whose `baseRef` is trunk's commit SHA (never a T3-made `t3/<hash>` branch name, per the runtime), the brief in `message` (opening with the router's absolute path and `Read it in full before any work.`), and a `modelSelection` from the code role. Leave `runtimeMode` and `interactionMode` unset so the owner runs in your modes. Launch has no retry key, so after a lost response check `t3_thread_list` before you launch again. A launched thread never wakes its launcher, so the brief carries your thread id and says to send each report below with `t3_thread_send` and `mode: "queue"` to it, and to stop when that call is refused. Outside T3 each owner is a background `Agent` in its own worktree. Such an owner has no `/loop`, so it babysits by rerunning the bare watcher in the foreground (`playbooks/babysit.md` step 6). Before the first owner starts in T3, confirm with `t3_thread_configuration` that this thread runs in `auto` or `full-access` mode, and ask the operator to switch it if it does not. A child's modes can never be broader than its parent's, so under a narrower mode every owner stalls on approvals. Those modes approve tool calls silently, so you hold the Always-pause list yourself ([the runtime's Questions](../references/runtime.md#questions)). Owners and their children run every command in the foreground, since a Claude child that leaves a background shell running can end its turn early. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill (`{{p3}}/skills/show-me-your-work/SKILL.md`), pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and `/p3:no-comments`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's CLAUDE.md and AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. Before each commit or push from its worktree, the owner stops every child that writes there, grandchildren included. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill (`{{p3}}/skills/swarm/SKILL.md`) and aggregate to one verdict. Record the model and effort each lane actually ran at, not the ones you asked for ([the runtime's Roles](../references/runtime.md#roles)). For a `delegate_task` lane, `task_status` names the model and `t3_thread_configuration` on its `childThreadId` names the effort. For an `Agent` lane, take the model from its transcript's assistant records and record the effort you passed. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (on the matching surface in [the runtime's Proof surfaces](../references/runtime.md#proof-surfaces), such as T3's `preview_*` tools or the terminal, or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When no independent lane could run, the verdict is not clean. Record `BLOCKED: independent review` and name the lanes that did run. When the lanes return, send every proven finding against the PR to the owner in one fix-forward (a `t3_thread_send` with `mode: "queue"` to a launched owner). A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge and returns. A fresh owner picks up the next self-contained item from the queue, per poteto-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm it with a prompt that runs this tick, per [the runtime's Waking](../references/runtime.md#waking). In T3 that is `schedule_task` with `schedule: {"type":"interval","everyMs":3600000}`, bound to this thread, because an unbound run starts a fresh thread from `main`. Report the returned cadence and next run time. Outside T3 it is `/loop 1h`. The scheduled task survives a T3 restart and `/loop` does not. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from the installed plugin, `<router-dir>/playbooks/autopilot-full.md`, where `<router-dir>` is the absolute directory of poteto-mode's SKILL.md that the tick prompt names, and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check (`t3_thread_read` on a launched owner), and collect the decision trails. In T3 also watch each owner's PR with `watch_pull_request`, since a launched owner never wakes you. A merge ends that watch without a wake, so the tick is how you learn of a merge the owner did not report. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Stand down a subagent with `TaskStop`, a delegated child with `task_cancel`, and a launched owner as in step 7, since `t3_thread_interrupt` does not stop async children. Confirm with `git status` that it stopped writing before its replacement takes the work. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. In Claude's agent list `completed` means the completion was notified, not that the agent exited. A delegated child can finish its turn and leave its run open, so its completion wake never comes. A bounded `t3_thread_wait` catches it. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick (`delete_scheduled_task`, or stop the `/loop`) only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. In T3, `t3_thread_interrupt` each owner, then `t3_thread_send` it the order. An interrupt does not stop async children, so the order tells each owner to stop its subagents and `task_cancel` its delegated children first. Cancel your own delegated lanes with `task_cancel`. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
